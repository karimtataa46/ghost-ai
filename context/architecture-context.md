# Architecture Context

## Stack

| Layer            | Technology              | Role                                                           |
| ---------------- | ----------------------- | -------------------------------------------------------------- |
| Framework        | Next.js 16 + TypeScript | Full-stack app with server/client boundaries                   |
| UI               | Tailwind + shadcn/ui    | Component composition and styling                              |
| Auth             | Clerk                   | User identity and route protection                             |
| Database         | Prisma + PostgreSQL     | Relational metadata: projects, collaborators, specs, task runs |
| Canvas           | Liveblocks + React Flow | Real-time collaborative canvas, presence, and cursors          |
| Background tasks | Trigger.dev             | Durable AI generation workflows                                |
| Artifact storage | Vercel Blob             | Canvas snapshots and generated Markdown specs                  |

## System Boundaries

- `app/api` — Authenticated request handlers: input validation, ownership checks, task triggering, and persistence.
- `trigger` — Long-running background jobs: AI design generation and spec generation.
- `lib` — Shared infrastructure: Prisma client, access control helpers, and utilities.
- `components` — UI composition: canvas surfaces, sidebars, dialogs, and interactive elements.
- `prisma` — Database schema (`prisma/schema.prisma` plus models in `prisma/models/`) and migrations. The generated client is written to `app/generated/prisma` (gitignored) and is used only through `lib/prisma.ts`. In development that module caches the client on `globalThis` together with a fingerprint of the generated model names and makes a new client when the fingerprint differs, so a `prisma generate` takes effect without restarting `next dev`; production creates the client once per process, as before.
- `data` — Legacy local directory. Not used for new artifacts.

## Storage Model

- **Database**: metadata, ownership, relationships, and task run records.
- **Vercel Blob**: generated artifacts — canvas snapshots at `canvas/{projectId}.json` and specs at `specs/{projectId}/{specId}.md`. Canvas blobs are `private` (the code's `CANVAS_BLOB_ACCESS` in `lib/canvas-storage.ts` must match how the Blob store was created: a public store rejects private uploads and the reverse), so they are only served through the canvas route, which checks project access. Spec blobs are `private` too (`SPEC_BLOB_ACCESS` in `lib/spec-storage.ts`, the same store, so the same setting) and are only served through the spec download route.
- Project records, spec records, and task run records belong in PostgreSQL.
- Canvas content and Markdown output are stored in and retrieved from Vercel Blob.
- The blob URL is stored in the database (`canvasJsonPath`, `filePath`) as the reference to the artifact.
- Liveblocks also keeps a room's Storage itself, so the canvas blob is a second copy, used to restore a room that starts empty and as the stable snapshot later AI generation will read; it is not the source of truth while people are editing.

## Auth and Collaboration Model

- Every project has a single owner (Clerk user ID).
- A project's ID is its Liveblocks room ID: `<slug>-<short suffix>` (lowercase letters, numbers, hyphens, at most 128 characters), built by the client and stored as the primary key through `POST /api/projects { id, name }`. A taken ID is `409`. Without an `id` the schema's cuid default applies.
- Projects can include additional collaborators, identified by email. A user's shared projects are the ones whose collaborators include their verified primary Clerk email (case-insensitive), minus projects they own.
- Only authenticated users can access protected routes.
- `proxy.ts` (not `middleware.ts`) enforces this: every route is protected by default, and only the sign-in and sign-up paths from `NEXT_PUBLIC_CLERK_SIGN_IN_URL` / `NEXT_PUBLIC_CLERK_SIGN_UP_URL` are public (falling back to `/sign-in` and `/sign-up` when a var is unset or empty). Those two vars must stay at `/sign-in` and `/sign-up`, the only auth routes that exist; using a different path requires adding matching pages under `app/` first.
- `/` redirects to `/editor` when signed in and to `/sign-in` otherwise. The editor chrome (`EditorShell`, `WorkspaceShell`) is rendered only under `app/editor/`.
- Identity and project access are checked through `lib/project-access.ts`: `getCurrentUser()` (Clerk user ID + verified primary email) and `findAccessibleProject(projectId, user)` (owner or collaborator, else `null`).
- Unauthenticated requests to `/api/*` get a JSON `401` from `proxy.ts` (not Clerk's redirect or 404), and every handler re-checks the user with `auth()` because it derives `ownerId` from it.
- Renaming or deleting a project itself is owner-only: a signed-in non-owner gets `403` (`lib/projects.ts`, `denyUnlessOwner`). Collaborators do not get these two actions. Deleting a project runs in three steps: set `Project.status` to `DELETING`, delete its Liveblocks room (`deleteRoom`), then delete the database row (and the canvas blob, and the project's spec blobs through `deleteProjectSpecBlobs`: the `ProjectSpec` rows go with the project by cascade, but their files are separate blobs). The room goes because the project ID is the room ID and the client may choose it: a surviving room could otherwise be claimed by whoever re-creates the ID. The status goes first because `findAccessibleProject` refuses a `DELETING` project, so a token request that arrives after `deleteRoom` cannot re-create the room. A failure in either later step leaves the project `DELETING` (closed to everyone, still listed in the sidebar), and the owner retries the delete, which `denyUnlessOwner` allows whatever the status. Removing a collaborator does not end a session that already holds a token (the token lifetime has not been measured); only the next token request is refused.
- Collaborators are managed through `app/api/projects/[projectId]/collaborators` (`GET` list, `POST { email }` invite) and `.../collaborators/[collaboratorId]` (`DELETE`). The owner and collaborators can list (`findAccessibleProject`, anyone else `404`); only the owner can invite or remove (`denyUnlessOwner`, `403` otherwise). Emails are stored trimmed and lowercased, one row per project and email (`409` for a repeat); the owner cannot invite their own email.
- There is no local user table. Collaborator names and avatars come from the Clerk Backend API at list time (`lib/clerk-profiles.ts`, matched on verified email addresses only); an email with no Clerk user, or a Clerk failure, falls back to showing the email.
- Only the owner or a collaborator can mutate other project resources.
- Liveblocks room tokens are issued only after verifying project membership, by `POST /api/liveblocks-auth` (`app/api/liveblocks-auth/route.ts`). Liveblocks sends `{ room }` (the project ID); the handler checks, in order: signed in (`401`), `room` is a non-empty string (`400`), `findAccessibleProject` passes (`403` for a missing project, one being deleted, and one the user may not open, the same answer for all), then makes sure the room exists (`getOrCreateRoom`, private: `defaultAccesses: []`) and returns an access token from `prepareSession` that allows `["*:write"]` on that one room (owners and collaborators both edit). The session carries `userInfo { name, avatar?, color }`: Clerk name (first + last, else username, else verified email, else `Anonymous`), the uploaded avatar (omitted when none; Liveblocks types `avatar` as a string), and a cursor color from `getCursorColor(userId)`.
- `liveblocks.config.ts` (project root) declares the global `Liveblocks` types: `Presence { cursor: { x, y } | null; thinking: boolean }` (`cursor` is in canvas / React Flow coordinates, not screen ones) and `UserMeta { id; info { name; avatar?; color } }`. The node SDK and the React hooks both read them, so the token route is type-checked against `UserMeta`. `Storage` declares one key, `shapeColors?: LiveObject<ShapeColors>` (the color picked for each shape, see Editor Data Flow). The canvas's own `flow` key (a `LiveObject` of `nodes` and `edges` maps) is not declared: `useLiveblocksFlow` creates and types it, and the two live side by side in the root. `aiStatus?: LiveList<AiStatusEntry>` is the AI status feed (see AI Generation Model). Declare other room data here as it is added.
- The server-side Liveblocks client is `getLiveblocks()` in `lib/liveblocks.ts`: created on first use from `LIVEBLOCKS_SECRET_KEY`, cached on `globalThis`, and throws `LIVEBLOCKS_SECRET_KEY is not set` only when called (not at import), so `next build` does not need the secret. Never expose that key client-side.

## Editor Data Flow

- `app/editor/layout.tsx` (server) loads the owned and shared project lists (`lib/projects.ts`) and passes them to `ProjectsProvider`, so the sidebar needs no client-side fetching on load. Each page renders its own shell inside it: `/editor` uses `EditorShell`, `/editor/[roomId]` uses `WorkspaceShell`.
- Mutations go through `hooks/use-project-actions.ts` → `lib/project-api.ts` → `app/api/projects`, then `router.refresh()` re-runs the layout. A navigation alone does not re-render a layout, so creating a project calls `router.push` and `router.refresh()`.
- `/editor` is the home; `/editor/[roomId]` is a project's workspace (the room ID is the project ID). It is a server component: signed out → `redirect("/sign-in")`; a missing project or one the user is neither owner nor collaborator of → `AccessDenied` (same screen for both); otherwise `WorkspaceShell` with the project, whose canvas area is `<CanvasRoom roomId={project.id} />`.
- The canvas (client components, mounted per workspace, not in a layout):
  - `components/editor/project-room.tsx` (`ProjectRoom`) sets up the room: `LiveblocksProvider` with `authEndpoint="/api/liveblocks-auth"` and `RoomProvider` for the project ID (keyed by it, so moving between projects starts clean) with initial presence `{ cursor: null, thinking: false }`. `WorkspaceShell` mounts it around the whole workspace, so the canvas and the AI sidebar share one room connection. `components/editor/canvas-room.tsx` (`CanvasRoom`) renders inside it a `relative` wrapper `div` (the canvas area) holding an `ErrorBoundary` (error fallback) around `ClientSideSuspense` (loading state), plus `PresenceAvatars` beside them (see Presence below). `ConnectionErrorListener` sits beside the Suspense boundary, not inside it, and forwards `ROOM_CONNECTION_ERROR` to the boundary. That error fires only once the client has given up (auth rejected, no access to the room, room ID changed), not while it retries a dropped connection.
  - `components/editor/canvas.tsx` (`Canvas`) calls `useLiveblocksFlow<CanvasNode, CanvasEdge>({ suspense: true, nodes: { initial: [] }, edges: { initial: [] } })` and passes the synced nodes, edges, and change handlers (`onNodesChange`, `onEdgesChange`, `onConnect`, `onDelete`) to `ReactFlow` with `ConnectionMode.Loose`, `fitView`, `MiniMap`, and a dot `Background`. The hook freezes its options on the first render and only seeds Storage when the room has no flow yet.
  - Adding nodes from the shape panel: `components/editor/shape-panel.tsx` makes six buttons draggable with a `application/x-ghost-shape` payload `{ shape, width, height }` (`lib/canvas-drag.ts`, which also validates it on read). The `Canvas` wrapper `div` takes `onDragOver` / `onDrop` from `hooks/use-shape-drop.ts`: a drop converts the cursor position with React Flow's `screenToFlowPosition` and calls the Liveblocks `onNodesChange` with an `add` change for the node from `createCanvasNode` (`lib/canvas-nodes.ts`: ID `<shape>-<timestamp>-<counter>`, type `canvasNode`, empty label, the shape's default color from `SHAPE_DEFAULT_COLORS`, the shape's width and height). That is how the node reaches the room's Storage; nothing writes React Flow state locally. Keyboard and touch cannot drag, so `useShapeDrop` also returns `addShapeAtCenter(payload)`, which `Canvas` passes to `ShapePanel` as `onAddShape`: it converts the center of React Flow's container (`useStoreApi().getState().domNode`) with the same `screenToFlowPosition`, offsets by half the node's size, and sends the same `add` change. `useReactFlow` needs a provider, so `Canvas` wraps a private `CanvasSurface` in `ReactFlowProvider`. `canvasNode` is registered through a module-level `nodeTypes` with `CanvasNodeRenderer` (`components/editor/canvas-node.tsx`), which takes `data` and the size from the node in the collaborative state and renders it with `CanvasShape` (`components/editor/canvas-shape.tsx`: CSS for rectangle, pill, circle; SVG for diamond, hexagon, cylinder, with path data from `lib/canvas-shapes.ts`). Nothing about a node's look is stored or computed outside the synced node. Each node also renders four connection handles (`top`, `right`, `bottom`, `left`, all `source`); with `ConnectionMode.Loose` a drag from any handle to any other creates an edge through Liveblocks' `onConnect`, which stores `{ id, source, target, sourceHandle, targetHandle }` plus whatever React Flow merged in from `defaultEdgeOptions` before calling `onConnect` (`type: "smoothstep"`, `markerEnd`, `style`: a hand-drawn edge carries them in the room, a template's edge does not). The look does not depend on what is stored: `defaultEdgeOptions` from `lib/canvas-edges.ts` is passed to `ReactFlow` and merged in at draw time.
  - Shape drag preview: `ShapePanel` keeps the drag in progress in local state (set on `dragstart`, cleared on `dragend`) and renders `ShapeDragPreview` (`components/editor/shape-drag-preview.tsx`) while it is set. It is UI state only and never touches Storage; the drop path above is unchanged.
  - Node editing (resize and label), both inside `CanvasNodeRenderer` and both through React Flow's change flow, so they reach Storage through the same Liveblocks `onNodesChange` as every other node change. Resize: a React Flow `NodeResizer` (shown while the node is selected, `keepAspectRatio` so only the scale changes, minimum `NODE_MIN_SIZE`) emits `dimensions` changes (and `position` when a top or left side moves); `@liveblocks/react-flow` writes the new `width` / `height` to the node in Storage, and the node re-renders from them. Label: an empty label draws a dimmed `Label` placeholder (`NODE_LABEL_PLACEHOLDER`, drawn by `CanvasShape` from the synced `data.label`, nothing stored); clicking it, or double-clicking the label box, sets a local `isEditing` flag (UI state, never synced) that swaps the label text for `NodeLabelEditor` (`components/editor/node-label-editor.tsx`, a textarea). Each keystroke calls React Flow's `updateNodeData(id, { label })`, which queues a `replace` change for that node into the same `onNodesChange`. The editor keeps its own draft while open, because the synced value comes back a render later; a label changed by someone else mid-edit shows once the editor closes. It closes on blur or Escape and keeps what was typed. The textarea carries `nodrag nopan nowheel`, and React Flow ignores its shortcuts (Backspace, Delete) while a text field is focused; React Flow already puts `nopan` on draggable nodes, which is why a double-click on a node does not zoom the canvas.
  - Shape color: the color belongs to the shape, not the node, so every node of a shape matches. It is kept in the room's Storage as `shapeColors` (a `LiveObject<ShapeColors>`, shape name to palette fill), next to the canvas's `flow` key: created empty with the room (`initialStorage` in `canvas-room.tsx`) and on the first pick in a room that predates it. `Canvas` reads it through `useShapeColorStorage` (`hooks/use-shape-color-storage.ts`, `useStorage` + a `useMutation`) and hands it to `ShapeColorsProvider` (`components/editor/shape-colors-provider.tsx`, a plain context so nothing under it needs a room): `getColor(shape)` returns the picked fill, else `SHAPE_DEFAULT_COLORS[shape]` (a value that is not a palette fill counts as unset), and `setColor(shape, fill)` writes it. `CanvasNodeRenderer` and `ShapeDragPreview` draw `getColor(shape)`; a node's own `data.color` is only what it was created with and is not drawn, so the same-color rule cannot drift, even for nodes created while someone else was changing the color. `ShapePanel` opens `ShapeColorToolbar` when a shape button is clicked, and a swatch calls `setColor`. Only the fill is stored: the text color is looked up from the palette when a node draws. No server call, no node is rewritten, and the pick syncs to every collaborator like any Storage change.
  - Canvas controls and shortcuts: `Canvas` gets the React Flow instance (`useReactFlow`) and the room's history handlers and state (`useUndo`, `useRedo`, `useCanUndo`, `useCanRedo` from `@liveblocks/react/suspense`). It passes the handlers to `useKeyboardShortcuts` (`hooks/use-keyboard-shortcuts.ts`: a `window` `keydown` listener for `+` / `=` / `-` zoom, Cmd/Ctrl + Z, Cmd/Ctrl + Shift + Z, Cmd/Ctrl + Y history, `A` switch to the select tool, and `H` switch to the hand (pan) tool, skipping inputs, textareas, and editable text) along with the instance, and renders `CanvasControls` (`components/editor/canvas-controls.tsx`, a bottom-left bar of zoom out / fit view / zoom in and undo / redo) with the same handlers and the `canUndo` / `canRedo` state. Zoom is React Flow's own viewport (local, never synced) animated through `ZOOM_ANIMATION` in `lib/canvas-zoom.ts`; undo and redo are Liveblocks' per-user room history, so they reverse that user's own changes to the shared flow and `shapeColors` and sync like any other edit. Nothing here adds Storage keys or changes the collaborative state setup.
  - Selection tool: `Canvas` keeps the active tool (`CanvasTool`, `"select" | "pan"`, `types/canvas.ts`) in local state (UI only, never synced; `lib/canvas-tools.ts` has `DEFAULT_CANVAS_TOOL`, `pan`) and spreads `getCanvasToolProps(tool)` onto `ReactFlow`: `selectionOnDrag` and `panOnDrag` for the tool, plus `SelectionMode.Partial` and `deleteKeyCode={["Backspace", "Delete"]}` for both. Multi-select, group drag, and deletion are React Flow's own: moving a selection is `position` changes and deleting is `remove` changes plus `onDelete`, both through the same Liveblocks `onNodesChange` / `onDelete` the canvas already passes, so nothing is written locally and no Storage key is added. Selection (`selected`) is not synced. Tool shortcuts: `Canvas` passes its `setTool` to `useKeyboardShortcuts` as `onToolChange`; `A` calls it with `select` and `H` with `pan`, the same as the control bar's buttons. They change only the tool, never the selection, so nothing is emitted through `onNodesChange`. (Earlier, `A` also selected every node through a `selectAllNodes` helper; that was removed on request.) Box selection and edges: React Flow's box selects the nodes it touches and only the edges connected to them, so `Canvas` also passes `onSelectionEnd` from `useBoxSelectEdges(onEdgesChange)` (`hooks/use-box-select-edges.ts`). The hook keeps the last `userSelectionRect` from the React Flow store (`useStoreApi().subscribe`, because React Flow clears it just before `onSelectionEnd`), converts it to canvas coordinates with the store's `transform`, asks `getEdgeIdsCrossingRect` (`lib/canvas-selection.ts`) which drawn edges (`.react-flow__edge` under the store's `domNode`) have a path that passes through it (the path's `getPointAtLength` samples tested as line segments against the rectangle), and sends a `select` change through `onEdgesChange` for each one that is not selected yet. That is the same kind of change React Flow makes for its own edge selection, which `@liveblocks/react-flow` applies with `edge.setLocal("selected", ...)`, so nothing is written to Storage or undo history. It runs once, when the box is released, so a crossed edge highlights on release rather than while the box is being drawn. It applies to any box React Flow draws (the select tool, and Shift + drag with the pan tool).
  - Persistence (autosave and restore), all in `Canvas`, outside the room's Storage: `PUT /api/projects/[projectId]/canvas` takes `{ nodes, edges }`, validates it (`parseCanvasSnapshot`, `lib/canvas-snapshot.ts`: fields are picked by name, so `selected`, `measured`, `dragging`, `resizing`, an edge's `type` / `markerEnd` / `style` and any other unknown keys never reach the blob and are not refused (an edge's text, `label`, is the one extra field kept), and the same canvas always serializes to the same string), uploads the clean copy to Vercel Blob at `canvas/{projectId}.json` (overwriting, no random suffix) and stores the returned URL in `Project.canvasJsonPath`; `GET` reads the URL from Prisma, fetches the blob (`useCache: false`, since the blob is overwritten on every save) and returns `{ canvas: { nodes, edges } }`, or `{ canvas: null }` when nothing was saved. Both are open to the owner and collaborators (`findAccessibleProject`, `404` otherwise); `400` for a body that is not a valid canvas; the blob URL is never returned to the client. The Blob work lives in `lib/canvas-storage.ts` (`saveCanvas`, `loadCanvas`, `deleteCanvasBlob`); if the project is deleted between the access check and the Prisma write, the just-uploaded blob is removed. Deleting a project also deletes its blob (after the row, best effort). The client side is `lib/canvas-api.ts`, `hooks/use-canvas-load.ts`, `hooks/use-canvas-autosave.ts`. Load: on mount, if the room has no nodes and no edges, `useCanvasLoad` fetches the saved canvas and, if the room is still empty when the reply arrives, adds it through the flow hook's own `onNodesChange` / `onEdgesChange` inside `history.disable` (shared with everyone, and not an undo step, so Undo cannot wipe a restore), then fits the view; a room that already has content is never fetched for, and the saved canvas is never applied over content. Autosave: `useCanvasAutosave` waits `AUTOSAVE_DELAY_MS` (2s) after the last change to `nodes` / `edges` (from anyone in the room, so the saved copy follows the shared state), serializes, and saves only if the string differs from the last saved (or initial) one, so selecting a node saves nothing; one request at a time, and a change that arrives mid-request starts a new debounce; a pending change is saved when the canvas unmounts. It stays disabled until the load has finished, so it can never replace the saved canvas with the empty one the editor starts with, and a failed load keeps it disabled (the Save button then retries the load). The canvas as it is when autosave is first enabled counts as already saved, so opening a project writes nothing. An empty canvas is a valid save, so clearing the canvas is saved and does not come back. The navbar's Save button gets its state from the canvas through `CanvasSaveProvider` (the same bridge pattern as the starter template importer).
  - Edge selection and deletion: `CanvasEdgeRenderer` (`components/editor/canvas-edge.tsx`) is registered with `ReactFlow` as `edgeTypes={{ [CANVAS_EDGE_TYPE]: CanvasEdgeRenderer }}` (`lib/canvas-edges.ts`, `CANVAS_EDGE_TYPE = "smoothstep"`), which replaces React Flow's built-in smooth-step component. Registering under `smoothstep` rather than a new `canvasEdge` type is deliberate: a hand-drawn edge is stored with `type: "smoothstep"` and a template's edge has no stored type (`defaultEdgeOptions` supplies it at draw time), so one registration draws both and no stored edge has to be rewritten. It draws React Flow's `BaseEdge` on `getSmoothStepPath` with the style and marker React Flow passes in (`defaultEdgeOptions`). Clicking an edge selects it (React Flow's own, local, never synced: `@liveblocks/react-flow` sets `selected` with `setLocal`). A selected edge draws `SELECTED_EDGE_STYLE` over its style (brand-color stroke, 2.5px, a brand-color glow; the glow is there because the arrow's color is baked into React Flow's marker and cannot follow the line), and, when it is the only selected edge, an `EdgeDeleteButton` just to the right of its midpoint (never on it, see Edge text; React Flow's `EdgeLabelRenderer`, `nodrag nopan`, scaled by `1 / zoom` like the live cursors so it stays the same size on screen). The button calls `useReactFlow().deleteElements({ edges: [{ id }] })`, which calls the `onDelete` prop, which is the Liveblocks flow hook's `onDelete` (the same one Backspace / Delete reach), so the edge is deleted from the room's Storage for everyone and is one undo step; nothing is written locally and no Storage key is added. A selection of several edges (a box selection also selects the edges between the nodes) shows no buttons; Backspace / Delete remove all of it.
  - Edge text: an edge's text is React Flow's own `label` field on the edge, a string (not `data.label` as a node's is): `@liveblocks/react-flow` already lists `label` among the edge fields it syncs, atomically, so it needs no `sync` config and no new Storage key. Double-clicking an edge (a `g` around `BaseEdge`'s wide invisible hit path in `CanvasEdgeRenderer`; the first click of the double-click has already selected it) or its text sets a local `isEditing` flag (UI only, never synced) that swaps the text for `EdgeLabelEditor` (`components/editor/edge-label-editor.tsx`, a one-line input styled like the text, sized by its content). The editor keeps its own draft and writes nothing while typing; Enter, Escape, or losing focus closes it once with the draft, and the renderer trims it and, if it changed, calls `useReactFlow().updateEdge(id, { label })` (the edge-side counterpart of `updateNodeData`: a `replace` change into the Liveblocks `onEdgesChange`). Writing it once on close makes an edit one undo step and one write, unlike the node label editor, which writes on every key. Cleared text is written as `label: undefined`, which Liveblocks' `reconcile` turns into a deleted key, so no empty `label` stays in Storage. The text is drawn in `EdgeLabelRenderer` on the edge's midpoint in a box that scales with the canvas (like node text; the delete button inside it is scaled back by `1 / zoom`), and the delete button sits to the right of what is on the midpoint, 4px (screen) from the text, or 16px from the midpoint when there is no text, never on the midpoint itself. That placement is a bug fix: the midpoint is where people double-click, the first click of the double-click selects the edge and shows the button, and a button centered there took the second click and deleted the edge instead of opening the editor (seen in the browser, two edges lost). The gap is also kept in screen pixels (`1 / zoom` applied to it), so the button stays clear of the line's 20px hit area at any zoom. A click on the text selects the edge because React passes events from a portal up to the edge's own handlers; for the same reason the editor stops key events from reaching the edge, whose handler would select it on Enter / Space and deselect it on Escape. React Flow's edge group already carries `nopan`, so a double-click on an edge does not zoom the canvas, and the label box has `nodrag nopan` for the same reason. The text is saved with the canvas: `parseEdge` (`lib/canvas-snapshot.ts`) keeps a `label` that is a non-empty string (and ignores any other value) and puts it after the handles, so saving, restoring, and the autosave comparison all include it.
  - Shared canvas types live in `types/canvas.ts`. Not built yet (see Starter System Designs for the starter templates, which are): a full color picker (the toolbar offers only the predefined pairs), a custom `canvasEdge` edge type (the type exists in `types/canvas.ts` but nothing uses it), AI.
  - Presence (avatars and cursors), all through Liveblocks presence, never Storage, so nothing is saved and nothing enters undo history. Sending: `Canvas` spreads `useCursorPresence()` (`hooks/use-cursor-presence.ts`) onto `ReactFlow` as `onMouseMove` / `onMouseLeave`: a move sends `updateMyPresence({ cursor })` with the pointer converted by `screenToFlowPosition` (canvas coordinates, so it lands on the same spot whatever each person's pan and zoom), a leave sends `cursor: null`. Liveblocks throttles these sends (its default 100ms; the `throttle` option is not changed). Drawing others' cursors: `LiveCursors` (`components/editor/live-cursors.tsx`) is a child of `ReactFlow`, drawn in React Flow's `ViewportPortal` so cursors pan and zoom with the nodes and are scaled by `1 / zoom` to keep a constant on-screen size. It lists others with `useOthersConnectionIds()` (changes only when someone joins or leaves), and each `LiveCursor` reads its own connection with `useOther(connectionId, selector, shallow)`, so one person's pointer re-renders only their cursor. The color is `info.color` from the session (the same value as the avatar's person). Avatar group: `PresenceAvatars` (`components/editor/presence-avatars.tsx`) is mounted by `CanvasRoom` beside the Suspense boundary (not inside it), so the Clerk `UserButton` in it stays visible while the room loads or fails; it uses the plain `@liveblocks/react` hooks (`useOthersMapped` in `hooks/use-room-participants.ts`), which are empty until the room connects. Both read the viewer's ID from the active Clerk session (`useAuth().userId`) and exclude any presence entry with that user ID, so the viewer's own second tab is neither an avatar nor a cursor; nothing is shown until Clerk has loaded. Avatars are one per person (several tabs of one person are one avatar), cursors are one per connection.

## Starter System Designs

- Prebuilt templates are static canvas snapshots stored in the codebase.
- Templates are loaded into the active Liveblocks room when a user imports one.
- Import can occur on canvas creation or from within the editor at any time. Built so far: from within the editor, through the workspace navbar's Templates button; import on canvas creation is not built.
- Template data follows the same node/edge schema as user-created canvas content.
- Templates do not require a separate database record; they are resolved by template ID at import time.

Implementation (`components/editor/starter-templates.ts`, `starter-templates-modal.tsx`, `template-preview.tsx`, `template-import-provider.tsx`, `hooks/use-template-import.ts`, `lib/canvas-preview.ts`):

- `CANVAS_TEMPLATES` is a constant list of `CanvasTemplate { id, name, description, nodes: CanvasNode[], edges: CanvasEdge[] }`, built with the shared canvas types. Nodes are positioned by center, sized by `SHAPE_DEFAULT_SIZES`, and carry their shape's default color; edges store only `{ id, source, target, sourceHandle, targetHandle }` (a hand-drawn connection stores the same plus the merged `defaultEdgeOptions`), so `defaultEdgeOptions` styles them. Nothing is saved: no template records, no user templates, no server call.
- Importing replaces the whole canvas through the existing collaborative state, in one `room.batch` (one undo step): `onDelete({ nodes, edges })` with everything currently on the canvas, then `onNodesChange` and `onEdgesChange` with `add` changes for copies of the template's nodes and edges, then React Flow's `fitView`. Clearing has to go through `onDelete`: the Liveblocks `onNodesChange` / `onEdgesChange` (`@liveblocks/react-flow` 3.24.3) treat a `remove` change as a no-op. `fitView` is queued by React Flow until every node is measured, so calling it right after the writes fits the new nodes.
- The Templates button and the modal live in `WorkspaceShell`, outside the Liveblocks room, but the handlers only exist inside the canvas. `Canvas` registers a stable importer with `TemplateImportProvider` (`useRegisterTemplateImporter`); the shell keeps it in state, calls it from the modal's `onImport`, and disables the button while there is none (loading, failed connection).

## AI Generation Model

### Design Generation

- Input: user prompt, project context, and current canvas state.
- Execution: durable background task via Trigger.dev.
- Output: structured node and edge updates written into the shared Liveblocks room.

- Trigger flow: `POST /api/ai/design { prompt, roomId, projectId }` checks, in order, signed in (`401`), a JSON object body, `prompt` (trimmed, 1 to 4000 characters) and `roomId` / `projectId` strings (`400`), `findAccessibleProject` (`403`, the same answer for a missing project and one the user may not open), and `roomId === project.id` (`400`; the project ID is the room ID). It then triggers the `design-agent` task (`trigger/design-agent.ts`, payload `{ prompt, roomId }`; what the task does is described below), stores a `TaskRun` row (`runId` unique, `projectId` with a cascading relation, `userId`, `createdAt`; compound index on `userId, projectId`), and returns `202 { runId }`. Failures after the checks return a JSON `{ error }` with a fixed message (`Could not start the design. Try again.`), never internal text, and the real error is logged on the server: a throw from `tasks.trigger` is `502`; a throw from the `TaskRun` insert is `500`, and because a run without a row could never be reached by a token (it would still edit the canvas, unseen and uncancellable), the route first makes a best-effort `runs.cancel` of the run it just started (a failed cancel is only logged). `POST /api/ai/design/token { runId }` looks the run up by `runId` and `userId` through `lib/task-runs.ts` (`404` for a missing run and for someone else's, the same answer) and returns `{ token }`, a Trigger.dev public token that can read only that run (`auth.createPublicToken`, `scopes.read.runs`, 1 hour). A throw from the lookup or from `createPublicToken` is a JSON `500 { error }` (`Could not get access to the design run. Try again.`). The run ID alone never grants access.

- Design agent (`trigger/design-agent.ts`, `runDesignAgent` run by the `design-agent` task, `maxDuration` 300, `retry.maxAttempts` 1: applying a plan is not idempotent, so a failure is reported once and never retried). Steps, each reported to the room: (1) start the AI's presence and post a `start` status; (2) read the canvas (`mutateFlow` from `@liveblocks/react-flow/node`, the headless counterpart of `useLiveblocksFlow`, on the same `flow` Storage key); (3) ask Gemini (`@ai-sdk/google`, `generateText` with `Output.object`, `gemini-flash-latest`, then `gemini-3.5-flash`, then `gemini-3.5-flash-lite`, each tried only if the one before errors, with the SDK's own retries off (`maxRetries: 0`; a daily quota 429 cannot be retried away, and each model has its own quota); a 429 from every model fails the run with "The AI service has reached its usage limit. Try again later."; key `GOOGLE_AI_API_KEY`) for a plan, in which every `add_edge` carries a one-to-three-word label (`label` is a required field of the plan schema: left optional, the model never wrote one, and actions without text send `""`, which the parser ignores); (4) apply the plan one action at a time, each in its own `mutateFlow` call, so collaborators watch the diagram grow; (5) post `complete` (or `error`) and clear the presence in a `finally`. All of it needs `GOOGLE_AI_API_KEY` and `LIVEBLOCKS_SECRET_KEY` in the Trigger.dev environment, not just in `.env.local`.
- The plan (`lib/design-actions.ts`): the model returns `{ summary, actions }` and every action is validated by `parseDesignAction` before use (the output is untrusted input; a malformed action is dropped and counted, the rest still run, at most 80). Actions: `add_node`, `move_node`, `resize_node`, `update_node` (label and/or shape), `delete_node` (its edges go with it), `add_edge`, `delete_edge`. They run in a fixed order (removals, changes to what exists, new nodes, new edges) so an edge always has its nodes. Rules enforced in code, whatever the model says: only the six `NODE_SHAPES`; a node's `data.color` is its shape's palette default (`SHAPE_DEFAULT_COLORS`; the canvas draws shape colors from `shapeColors`, so the model does not choose colors); size clamped to `NODE_MIN_SIZE`..400 and defaulting to the shape's default; positions are node centers, snapped to a 20px grid, and a node that would come within 60px of another is moved to the nearest free grid spot; edge handles are chosen from the nodes' relative positions (not by the model); an edge needs two existing nodes and is skipped if that pair is already connected; an action that does not fit the canvas as it is now (unknown node, taken id) is skipped with a logged reason. Prompt text is in `lib/design-prompt.ts` (system instructions, and the canvas described as one line per node and edge).
- AI presence (`lib/ai-presence.ts`): the agent is a participant with user ID `ghost-ai` and info `{ name: "Ghost AI", color: --accent-ai-text }`, set through `getLiveblocks().setPresence` (no connection). Presence is `{ cursor, thinking }` as for people: `thinking: true` for the whole run, `cursor` moved to the center of each node it touches. Because it is ordinary presence, the existing avatar group and live cursors draw it with no client change; a cursor badge shows a small spinner while that participant has `thinking: true` (`live-cursors.tsx`), and the AI sidebar reads the same flag (`hooks/use-ai-thinking.ts`: any other participant, or you, with `thinking`) to lock its chat input. It carries a 30s TTL renewed every 10s while the task runs; `clear()` sets no cursor, not thinking, and the 2s minimum TTL, so a crashed task cannot leave the AI in the room.
- AI status feed (`lib/ai-status.ts`): a Liveblocks Feed named `ai-status-feed` (`AI_STATUS_FEED_ID` in `types/tasks.ts`), not Storage and not a second realtime channel. Each message's data is `AiStatusMessage` (`types/tasks.ts`): `{ text?: string; kind?: start | progress | complete | error }`, generic so spec generation can reuse it. Written only by background tasks through `publishAiStatus(roomId, kind, text)` (node SDK `createFeedMessage`); the first write in a room creates the feed and trims it to the newest 30 messages (the server lists newest first, so a late joiner's first page has the latest). Messages from the design agent: start, "Reading the canvas", "Planning the design", one line per group of actions ("Adding 6 components", ...), then complete with the model's summary and the number of changes, or error. Read by the sidebar only: `hooks/use-ai-status.ts` (`useFeedMessages` from `@liveblocks/react`, the latest message by `createdAt`) runs its data through `parseAiStatusMessage` (hand-written validation in `types/tasks.ts`; `zod` is not a direct dependency) and `AiStatusIndicator` shows that one line, never the history.
- Errors: a status and presence failure is logged and never stops the run. A failure in the model call, the plan, or the canvas write posts one `error` entry, clears presence, and rethrows so the run shows as failed. Only `DesignAgentError` messages (not configured, unreadable plan, no changes, nothing applicable) are shown; any other error is logged in full and shown as a generic line, so no provider detail reaches the room. A failure after some actions leaves them on the canvas and says "Stopped after N of M changes". Changes are written straight to the room, outside any user's undo history.

- AI chat feed (`ai-chat`, `AI_CHAT_FEED_ID` in `types/tasks.ts`): a second Liveblocks Feed in the same room, for the sidebar conversation between the people in it. It is never mixed with `ai-status-feed`: the status feed is written by background tasks and read as one line, the chat feed is written by clients and read as a history. Each message's data is `AiChatFeedMessage` (`{ sender: { id, name }, role: user | assistant, content, timestamp }`), defined by `aiChatMessageSchema` (Zod) and checked with `parseAiChatMessage` before anything renders, since anyone with write access to the room can write to a feed. The client creates the feed on first use (`hooks/use-ai-chat-feed-ready.ts`), then `hooks/use-ai-chat.ts` reads it (`useFeedMessages`, sorted by the server's `createdAt`) and sends with `useCreateFeedMessage` using the viewer's `useSelf` identity (the Clerk user ID and display name from the session). No server route is involved and nothing triggers an AI task; `role: "assistant"` messages (sender `AI_SENDER`, "Ghost AI") are written by the browser that started a design run, when the run ends (26): its summary, or the failure reason. History is not trimmed.

### Spec Generation

- Input: current canvas graph and project context.
- Execution: durable background task via Trigger.dev.
- Output: Markdown technical spec, stored in Vercel Blob (`specs/{projectId}/{specId}.md`) and linked to the project in the database. The `generate-spec` task (27) returns the Markdown as the run's output and, since 28, also saves it (see Persistence and download below).

- Trigger flow (27): `POST /api/ai/spec { roomId, chatHistory, nodes, edges }` checks, in order, signed in (`401`), a JSON object body (`400`), the body against `specRequestSchema` (`lib/spec-input.ts`, Zod; `400 { error }` naming the first bad field, such as `nodes: Add at least one component to the canvas before generating a spec`), and `findAccessibleProject(roomId, user)` (`403`, the same answer for a missing project and one the user may not open). The project comes from the room (the project ID is the room ID) and the signed-in user; a `projectId` in the body is dropped by parsing and never read. It triggers the `generate-spec` task with `{ projectId, roomId, chatHistory, nodes, edges }` taken from the parsed request and the resolved project, stores a `TaskRun` (same table and helpers as design runs, `lib/task-runs.ts`), and returns `202 { runId }`. Failure handling is the design route's: a throw from `tasks.trigger` is `502`, a throw from the `TaskRun` insert is `500` after a best-effort `runs.cancel`, both with the fixed message `Could not start the spec. Try again.` and the real error logged. `POST /api/ai/spec/token { runId }` looks the run up by `runId` and `userId` (`findOwnedTaskRun`; `404` for a missing run and for someone else's, the same answer) and returns `{ token }`, a Trigger.dev public token that can read only that run (`auth.createPublicToken`, `scopes.read.runs`, 1 hour); a throw is a JSON `500` (`Could not get access to the spec run. Try again.`). `TaskRun` has no task-type column, so a run's owner can get a token from either token route for any of their runs; the token only reads that one run.
- Input limits (`lib/spec-input.ts`, shared by the route and the task so they cannot drift): the canvas is reduced to what a spec needs, nodes to `{ id, data: { label, shape } }` and edges to `{ id, source, target, label? }`, so position, size, color, and React Flow's local state never reach the task. At least 1 and at most 200 nodes and 400 edges (`400` beyond); a label is trimmed and clipped to 200 characters, not refused, since the editor has no limit; `chatHistory` items keep `role` and `content` (the `ai-chat` feed's own schema) and only the newest 30 are used, so a long room history is cut rather than refused.
- Spec task (`trigger/generate-spec.ts`, `runGenerateSpec` run by the `generate-spec` task, exported as `generateSpec`; `maxDuration` 300, `retry.maxAttempts` 1): validates its payload with the same schema (a failure is reported as `The canvas could not be read. Try again.`), builds the prompt (`lib/spec-prompt.ts`: a fixed outline of sections, the diagram as one line per component with who it sends to and receives from, worked out in code because the model reads arrow direction wrongly from a flat list, and one line per connection, then the chat), and asks Gemini (`@ai-sdk/google`, `generateText`, the same model list and 429 handling as the design agent through `lib/ai-models.ts`, `GOOGLE_AI_API_KEY`, 90s per model, SDK retries off). A reply that is empty or cut off counts as a failure of that model; a 429 from every model reports the usage limit. It returns the Markdown as a plain string (a code fence around the whole document is removed). The prompt treats the diagram and the chat as user content to describe, not instructions. It does not touch the canvas, presence, or the status feed.
- Run metadata is how the browser follows a spec run (`useRealtimeRun` reads `run.metadata`): `status` (`started`, `generating`, `complete`, `error`; `SpecRunStatus` in `types/tasks.ts`) and `message`, a line safe to show. Failures log the real error and throw only a fixed user-facing message, so the run's `error` (readable by whoever holds its token) never carries provider detail. Generation changes nothing outside the run, but it is not retried: the model list is the retry, and a second attempt would repeat minutes of failing calls and flip the status from `error` back to `generating`.
- Persistence and download (28): Prisma keeps metadata, Blob keeps the Markdown, as for the canvas. `ProjectSpec` (`prisma/models/project-spec.prisma`: `id`, `projectId` with a cascading relation, `filePath`, `createdAt`) has no content column. All spec Blob work lives in `lib/spec-storage.ts`. The save runs inside the `generate-spec` task, right after the model answers, because it is the one server-side step that follows generation without a client call: `saveSpec(projectId, markdown)` makes the spec ID first (`crypto.randomUUID()`; it is part of the path), uploads to `specs/{projectId}/{specId}.md` (`private`, no random suffix, never overwritten: every generation is a new spec, unlike the canvas's one blob per project), then inserts the row with the blob URL, and removes the new blob if the insert fails (e.g. the project was deleted meanwhile). The task therefore needs `DATABASE_URL` and `BLOB_READ_WRITE_TOKEN` in the Trigger.dev environment, not just in `.env.local`. A failed save fails the run with its own fixed line (`The spec was written but could not be saved. Try again.`; the real error is logged), since a spec nobody can download is not a finished one. On success the run's metadata gets `specId` beside `status: complete` (`SpecRunMetadata`), and the output is still the plain Markdown.
- Download: `GET /api/projects/[projectId]/specs/[specId]/download` checks, in order, signed in (`401`), `findAccessibleProject` (`403`; one answer for a missing project, one being deleted, and one the user is not on, so a project ID's existence is not revealed, as in the AI routes; the owner and collaborators can download), the spec exists in that project (`findProjectSpec` looks up by `id` and `projectId`, so another project's spec is `404`, not found, even for someone who can open both), and the blob is still there (`404`). It streams the file from Blob (`openSpecFile`) and never returns the blob URL: `Content-Type: text/markdown; charset=utf-8`, `Content-Disposition: attachment; filename="<project-name-slug>-spec-<yyyy-mm-dd>.md"` (ASCII, built from the project's name and the spec's creation date by `specFilename` in `lib/spec-filename.ts`; not stored), `Cache-Control: private, no-store` (the answer depends on who is asking), `X-Content-Type-Options: nosniff`. It sends no `Content-Length`: `get` reports the upstream response's own `Content-Length`, which is absent (read as `0`) when Blob answers chunked or compressed, as it does for anything but a tiny file, and forwarding that made the browser read an empty file (found in 29, with a 4.7 KB spec; a 97-byte one was fine). `openSpecFile` therefore returns only the stream, and the body goes out chunked.
- List (29): `GET /api/projects/[projectId]/specs` checks, in order, signed in (`401`) and `findAccessibleProject` (`403`, the same single answer as the download route; owner and collaborators), then returns `{ specs: [{ id, filename, createdAt }] }`, newest first (`listProjectSpecs` in `lib/spec-storage.ts`, capped at 100 because every generation adds a spec and nothing removes one), `Cache-Control: private, no-store`. Metadata only: `filePath` is not selected, so no blob URL can reach the response, and the filename comes from the same `specFilename` as the download, so a list entry names the file it downloads. There is no route that returns a spec's content as JSON; the preview reads the Markdown from the download route.
- Specs tab (29, client only): `AiSpecsTab` (`useRoom().id` is the project ID) loads the list through `hooks/use-project-specs.ts` → `lib/spec-api.ts` (`listSpecs`) when the tab mounts, so it is fresh on each visit (an inactive tab panel unmounts). Clicking a card opens `SpecPreviewDialog`, which mounts its body only while open: `hooks/use-spec-content.ts` → `loadSpecContent` does a `fetch` of the download route and reads the text (a `fetch` ignores `Content-Disposition`), holds it in that hook's state, and drops it when the dialog closes; nothing is cached or put in shared state. Download is a plain `<a href="…/download" download>` to the same route, so the browser saves the file itself and the client never sees a blob URL. The Markdown is drawn by `react-markdown` + `remark-gfm` (`components/editor/spec-markdown.tsx`), which builds React elements and does not render raw HTML; images are disallowed because the text is model-written from collaborator input and an image URL would make every previewer fetch it.
- Generating from the Specs tab (29 follow-up, client only): `Generate Spec` (`components/editor/spec-generate-section.tsx`) reads the canvas once, at click time (`room.getStorage()`, then `root.toJSON()` through `readSpecCanvas` in `lib/spec-canvas.ts`, which keeps only `{ id, data: { label, shape } }` per node and `{ id, source, target, label? }` per edge and skips anything malformed, because Storage outlives the code that wrote it), and the conversation from the `ai-chat` feed (`useAiChat`: role and content), then calls `startSpecRun` (`lib/spec-api.ts`, which uses `startTaskRun` in `lib/task-run-api.ts`: `POST /api/ai/spec`, then `POST /api/ai/spec/token`; the design run uses the same helper). `hooks/use-spec-run.ts` follows the run with `useRealtimeRun` and the run-scoped token, shows the run's `message` metadata as the status line, and when the run completes calls back so the list reloads and shows the spec the task saved. Whether a run is active, and how it ended, are worked out from the run on each render and not stored, so a finished run is never read as the next one. A canvas with no components is refused in the browser before any request (the server refuses it too). The button is locked while the run is active and while anyone's `thinking` presence is set, so a spec is not written from a canvas the AI is half-way through drawing, and until the `ai-chat` feed exists, because the generator reads it. Only the person who pressed the button follows the run; nothing is written to `ai-status-feed` or presence for specs, and leaving the Specs tab unmounts the follower (the run and its saved spec are unaffected).

## Invariants

1. Request handlers do not run long-lived AI work — that belongs in background tasks.
2. Metadata and large generated artifacts are stored in separate layers.
3. Auth and ownership are enforced at every mutation boundary.
4. Client components are used only where browser interactivity or real-time state requires them.
5. The canvas schema must remain consistent between user-created content and imported templates.
